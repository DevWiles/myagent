这里只留一种条目：**当时想不通、后来才弄明白的事**。判据是「下次再撞见，看一眼这条能省掉几小时」。

## 2026-09-22 · 加第二块屏之前，先去数了一遍别人是怎么做的

想给 myagent 加个手机端，先调研了一圈 2026 年的「Claude Code on Android」生态。
它们看着是同一件事，其实分三条路线，工程性质差一个数量级：

- **手机本地跑完整 agent**：APK 里塞一套 proot Linux（Mobile-Harness 359★、AnyClaw 544★、
  claude-code-android 246★）。工作量 100% 在跟 Android 沙箱搏斗——
  SELinux 从 API 29 起禁止执行应用数据目录里的二进制（所以这类 app 全部钉死 `targetSdk=28`、
  只能 sideload）、seccomp、没有完整 PTY（`vim`/`top` 一律翻车）。
- **手机当远程客户端**：Happy 23.9k★（CLI wrapper + relay + RN 端）、claudecodeui 13.8k★（响应式 Web）。
- **原生瘦客户端**：opencode-android 那种，连自建 server。

**决定走第二/三条，一行 proot 代码都不写。** 两个理由：路线一的工程量跟「搞懂 agent 怎么转」
零相关，而这是个学习项目；何况后端是 JVM，往手机里塞 JVM 更没道理。
顺带一个印证：Anthropic 官方的 Remote Control 给的答案也是这条——
代码执行和文件访问留在本机，手机只是另一块屏。

有两类项目**看过就该躲开**：血统来自 2026-03-31 那次 Claude Code 源码泄漏的
clean-room 重写（法律状态至今没定论），以及 AGPL 的（只能看设计不能抄代码）。
另外搜索结果里混着一堆**标题一字不差的镜像仓库**，评估这类项目别看 star，看 commit 曲线。

### 加第二个客户端，最先暴露的是协议里「只有一个客户端」的假设

终端和后端同生共死——连接断了进程也没了，所以协议里从来不需要「补发」这个概念。
手机不一样：切个后台、过个电梯，连接必断而后端还活着。

于是补了 `seq` + 留底 + `since=` 重连补发。三条当时想清楚的边界：

1. **只有广播事件编号**。`error`、`session_list` 这些定向回执不编号——
   它们答的是某一次具体的问，问的人都断线了，答案没有别人可给。
2. **留底装不下时如实发 `replay_gap`**。静默跳过的话，转录看起来完整、实际少了一段，
   这种错没人查得出来。**撒谎比缺口糟。**
3. **编号和播出必须在同一把锁里**。分开的话，补发出去的序列和当时播的顺序对不上——
   而这种错只在并发时偶现。

客户端那边对应一条：补发和实时会重叠，**按 seq 去重**（小于等于已见最大的直接丢），
顺序和完整性就都有了。

### 两块屏之间，真正危险的不是 UI 不一样，是语义漂移

手机端的 reducer 是照着 `tui/src/store.ts` 一条条对着写的，包括那些看起来可以「优化掉」的分支：
`thought` 和流式重复时不打第二遍、`done` 只在流式没走通时兜底、工具调用按 id 而不是「最近那个」配对、
压缩进度条原地更新而不是每条 append。

理由不是洁癖：**查协议 bug 时，「终端上对、手机上错」和「两边都错」是完全不同的两条排查路径**，
语义漂移会把前者伪装成后者。

### 一个 Android 的老坑，和一个新坑

老坑：`AgentApp` 忘了写进 Manifest 的 `android:name`，
症状是 `ClassCastException: android.app.Application cannot be cast to AgentApp`——
自定义 Application 不注册就是个摆设，而报错发生在 Activity 里，指向的是用它的那一行。

新坑：`SessionState.link` 的初始值给了 `CONNECTING`，于是**没配对过的首屏直接进了会话页**。
「连接中」和「还没开始连」是两个状态，混用一个枚举值就会这样。初始值该是 `CLOSED`。

## 2026-09-21 · 代码高亮：查了一遍 Claude Code，结论和我自己的三个方案都不一样

界面里代码块整块一个平色。我先给出三个方案（加 wasm / 入库 / 自己写 lexer），
然后去拆了 Claude Code 的二进制（Bun 编译的单文件，280MB，一部分是 JSC 字节码，
但**大块 JS 源码是明文**，strings + dd 就能读）。

答案是**第四个**：它用 **highlight.js 11.11.1**，不是 tree-sitter。证据链：
全量语言定义 + 扩展名映射 + 语言显示名表在包里；全局设置有 `syntaxHighlightingDisabled`；
插件清单 schema 里有 `syntaxHighlighting.hljsLanguages`，来源限 npm:/github: 且**强制 SRI**，
注册时跑一次 `highlight("")` 冒烟测试，失败就 unregister 并发 telemetry。
它自己还内置了一门 hljs grammar（Cedar）。

顺带两个发现：HTML artifact 是**另一条独立的路**（注入客户端 hljs 运行时，带 feature flag、
字符预算、`data-claude-hljs-claimed` 幂等标记）；终端 diff 做到了**词级**
（主题键里有 `diffAddedWord`/`diffRemovedWord`），比我们现在的行级细一层。

**教训：拿不准技术选型时，去读一个把这件事做对了的实现，比自己列三个方案靠谱。**
我那三个方案全部建立在「必须用 tree-sitter」这个没人验证过的前提上——
而那个前提只是因为 OpenTUI 恰好用它。

### 为什么 tree-sitter 在这儿是错的

OpenTUI 只捆 5 个 parser（js/ts/markdown/markdown_inline/zig），每加一门语言要 400KB~1.4MB 的 wasm。
更硬的一道坎：markdown parser 的 `infoStringMap` **只认 js/jsx/ts/tsx/md 这几种围栏标记**，
其余语言的 ``` 块压根不会被注入高亮。也就是说哪怕补上 java 的 wasm，```java 仍然不上色。

换 hljs 之后是纯 JS、无二进制、离线可用，`lib/common` 36 种语言涵盖了 java/python/go/rust。

### 走 token 树，不解析 HTML

`hljs.highlight()` 返回的 `value` 是 HTML。正则抠 `<span>` 能做，但要处理实体转义，
而**代码里恰恰全是 `<` `&` 这些字符**——少解一个就在屏幕上显示成 `&amp;&amp;`。
`_emitter.rootNode` 直接给结构化 token 树，一个字都不用解码。

代价是 `_emitter` 带下划线、半私有。所以两头都兜住：认不出结构就整段退回纯文本（不抛异常），
外加一条**依赖契约测试**（`treeShapeIsIntact`）——升级 hljs 之后形状变了会当场红，
而不是等用户发现代码块全变白。**半私有 API 可以用，但必须配一条会响的警报。**

## 2026-09-21 · 并发：三个层面一条规矩，和两个「串行时代」埋的雷

这一期给工具调用、计划任务、圆桌席位加并发。设计上最后收敛成一条规矩管三处——
**读共享、写独占**——因为它一石三鸟：写任务独占运行，同时解决了「两个写任务改同一个
文件的隐式冲突」「审批框一次只能弹一个」「审批的 origin 是个全局 volatile、并发会张冠李戴」
三件事。第三件是排查时才意识到的：会开口要审批的只有 mutates 角色手里的工具，
而独占意味着弹框那一刻场上只有它，origin 想错都错不了。

### 一、`PromptRepository` 的 HashMap 在并行子任务下炸了

并发测试第一次跑，五个 ANALYSIS 任务里偶发两三个失败，报的是执行体抛异常。
栈指向 `PromptRepository.loadRequired` 的 `HashMap.computeIfAbsent`——
提示词缓存是普通 HashMap，而装配发生在**每次构造 Agent** 时，并行的子任务同时
构造各自的 Agent，直接 `ConcurrentModificationException`。

这个雷是串行时代埋的：当时「同一时刻只有一个 Agent 在构造」是隐含成立的，
没人写下来，也没人守着。并发一开，第一个炸的不是精心设计的调度器，
而是一个八竿子打不着的缓存。**「进程里只有一条线在跑」是一条从没被声明过的全局假设，
开并发之前得把它想成默认为假。**症状也典型：偶发失败、重跑又好——
要不是测试里恰好五个任务一起跑，上线后没人查得到这儿。

### 二、工具流水号：服务端看着事件顺序补号，这套编号法死于并发

协议里 `tool_started`/`tool_finished` 靠 `id` 配对，而这个号原来是**服务端**编的：
看见一条 started 就 `++`，看见 finished 就取当前值。它建立在「工具严格串行、
开始和结束必然相邻」上——并行凑批之后，两条 started 会背靠背到达，第二条把号推进了，
先到的那条 finished 就配给了错的调用。审计那边同病：暂存参数用的是单个 volatile 字段，
「上一个开始的」不再是「这次结束的」。

解法是把号搬回**源头**：Agent 在发起调用那一刻编号（进程内全局递增，因为计划里
几个子 agent 同时在发），事件自带 id，服务端只是转发。审计的暂存改成按号建表。
**凡是「靠顺序隐式配对」的地方，并发后都得改成「靠 id 显式配对」**——
顺序是串行送的免费午餐。

### 三、测试假件的锁把被测的并发锁没了

给 `FakeRunner.run` 加 `synchronized`（并行的席位会同时来记账）之后，
「两席互相等对方开跑」的测试必然超时——剧本在锁里跑，两席根本进不去同一个方法，
被测的并发被测试自己的锁串行化了。改成记账在锁里、剧本在锁外。

反过来的教训更值钱：**验证「真的并发了」，用互相等待的 latch 比测耗时可靠**——
两个任务各自等对方开跑才返回成功，串行执行永远等不到，不并发就是确定性失败，
而不是「今天机器快就碰巧过了」。

## 2026-09-20 · 审批系统：三个洞都是「真跑一遍」才掉出来的

这一期做 HITL 审批。骨架早就有了（守卫 → `ApprovalPolicy` → `RemoteApproval` → 确认框），
所以本以为是加功能，结果动手之后发现要修的是**旧设计里几处方向性的错**。
三个都不是想出来的，是跑出来的。

### 一、`mvn test & rm -rf build` 整条被判成 SAFE

准备让授权规则复用 `CommandGuard.splitSegments` 时，顺手写了个探针把几种写法过一遍：

```
mvn test && rm -rf build     NEEDS_APPROVAL
mvn test &  rm -rf build     SAFE          ← ？
mvn test ;  rm -rf build     NEEDS_APPROVAL
```

分隔符表里有 `;` `&&` `||` `|`，**独独漏了单个 `&`**。于是 `commandName()` 只看到第一个
token `mvn`，在安全名单里，整条放行——后半句悄悄跑了。这个洞在加授权规则之前就存在，
只是没人写过带 `&` 的命令。

补的时候不能简单加一条 `.replace("&", "\n")`：`2>&1` 和 `&>out` 里的 `&` 不是分隔符，
切开会得到 `2>` 这种「未知命令」，于是**每条带重定向的命令都要问一次人**——
而被问烦的用户会一路按同意，那才是真正的损失。最后用的是
`(?<![<>&])&(?![>&0-9])`，两侧都验过。

> 通则：**一道闸的边界条件，要在「漏判」和「误判」两个方向上各试三条**。
> 只试漏判会留后门，只试误判会把闸变成摆设。

### 二、推荐给用户的那条规则，会顺手授权多删一个目录

「以后都同意」现在存的是一条有范围的规则，由代码从这次的命令推导、用户挑松紧。
推导逻辑写完自测都过，真拿 `rm -rf target` 跑了一下：

```
  rm -rf target
▸ rm -rf target *        ← 默认推荐这一档
  rm *

rm -rf target            规则=ALLOW   守卫=NEEDS_APPROVAL
rm -rf target src        规则=ALLOW   ← 用户只看见过 target
rm -rf target ~/Documents 规则=ALLOW   守卫=FORBIDDEN（纯属运气）
```

结尾那个 `*` 的意思是「后面还可以跟参数」。对 `mvn test -X` 这是放宽，
**对 `rm -rf target src` 这是又授权了一个删除目标**——而用户点头那一刻，
屏幕上只有 `target`。第三行没出事是因为 `~` 撞上了 FORBIDDEN，
在审批之前就被拦了；靠的是运气，不是设计。

区别不在命令本身，在**多出来的参数是什么性质**：是选项，还是又一个作用对象。
而这个区分 `CommandGuard.DESTRUCTIVE_COMMANDS` 已经列过了——它定义的正是
「参数指向会被销毁的东西」。所以破坏性命令只给「一字不差」一档，
复用那张表而不是另列一份：两份表迟早分叉，分叉处就是意外授权。

> 通则：**通配符的含义取决于被通配的位置上原本站着什么。**
> 同一个结尾 `*`，在选项位上是便利，在目标位上是授权。

### 三、`curl https://x.com *` —— 一档既没用又比精确松的选项

推导逻辑把「命令名之后第一个非选项 token」当子命令。对 `mvn test`、`npm run` 都对，
对 `curl https://x.com` 就荒唐了：推出来的中间档是 `curl <这个URL> *`，
比精确匹配松，又没松到有用，还会被当成默认选走。改成：这个 token 看着像路径或 URL
（含 `/` 或 `:`）时不给中间档，默认**退回最紧的那一档**。

默认值的方向要固定：**拿不准就紧**。松的那一档可以让用户按 → 挑到，
紧的那一档如果错过了，用户不会知道自己本可以更保守。

### 四、为什么把「本会话都同意」整个删掉

老实现里 `always` 是 `RemoteApproval` 上的一个布尔位。按一次，
这个会话里所有危险动作全部静默放行——为了批一条 `mvn test`，
顺手授权了 `curl`、`rm` 和覆盖任意文件。

它治的病是对的（审批疲劳是这类系统唯一真正的失败模式），治法是错的：
**它靠少看东西来少问**。而这两件事本来可以分开——

「这个动作危险吗」没有唯一答案，得问人；
「它匹不匹配已授权的规则」**有**唯一答案、可由代码推导、能被测试钉死。
以前没有「规则」这个概念，两件事糊在一起，于是唯一能做的「少问」就只剩全局开关。
拆开之后：算得出来的归 `PolicyGate`，算不出来的才升到人那儿。

这和放弃 RAG 时那条判据是同一条：**判据是「答案可不可推导」，不是「信不信谁」**。
上一期它决定了检索不建索引，这一期它决定了审批怎么分层。

### 五、跑通之后才发现审计少了一笔

端到端跑真模型那轮，一切正常：确认框出来、回 `always`、规则落盘、第二次不再问。
翻审计日志的时候才想到一件事：**规则存下之后，被它放行的动作不再产生审批记录**。
事后查账的人看到某个时间点之后危险动作突然没人批了，会以为审批被绕过了。

所以那一条 `approval` 记录里必须带上 `remembered`——它是那段「静默期」唯一的解释。

> 通则：**任何一个「以后不再报告」的开关，它自己被打开的那一刻必须留痕。**
> 否则日志的沉默会被读成异常，而不是被读成授权。

### 顺带

- 确认框的三个交互态（表态 / 挑规则 / 补话）放在 store 里，不放组件里。
  矮终端上那个框可能压根不渲染，而后端还阻塞等着——状态跟着组件走的话，
  那种终端上按 `a` 没有任何反应。这条纪律是 Ink 版就吃过的亏，按键处理同理。
- `~/.myagent/policy.json` 只做用户级，不做项目级。项目级听起来更「企业」，
  但 **agent 读的仓库和定策略的仓库是同一个**：一个 PR 往 `allow` 里塞条规则，
  下一个人在这仓库里跑 agent 时就已经被授权了。真要做，硬规矩得是
  「项目级只能收紧，放宽一律无效」。
- diff 是自己写的 LCS，先掐首尾公共部分。不是为了快——是为了让三千行的文件
  掐完只剩十几行要比，表格自然就不会爆。

## 2026-09-20 · 要做的 RAG，Claude Code 做过、又整套拆掉了

本来这一期是「SQLite + Embedding 给 agent 加代码检索」，图都画好了：代码库 → 分块 →
embedding → 向量库，查询那侧同一个模型编码、cosine 召回 Top-K、组装进上下文。
动手前顺手查了一下同类产品怎么做的，结果把整个方案掀了。

**第一个发现是硬的：DeepSeek 根本没有 embeddings 端点。**

```
POST https://api.deepseek.com/embeddings  →  404
GET  /models  →  只有 deepseek-flash、deepseek-v4-pro 两个 chat 模型
```

也就是说向量化必须引入第二个服务商、第二个 key、第二套配置——而这还只是成本。

**第二个发现要命得多：Claude Code 做过这件事，后来把整套删了。**
证据不用外求，本机就装着一份（`~/.local/share/claude/versions/`，280MB 的单体二进制）：

| 在二进制里搜 | 命中 |
|---|---|
| `ripgrep` | 289 —— rg 的二进制直接打进包里，连 man 页和 Grep 工具的说明词都在 |
| `text-embedding` / `sqlite-vec` / `faiss` / `vector_store` | **0** |
| `vectorSearch` | 8 —— 全是内置 AWS Bedrock SDK 的 `KnowledgeBaseRetrievalConfiguration`，与代码检索无关 |

公开说法对得上：Claude Code 的作者说他们**一开始就是 RAG + 本地向量库**，
后来发现 agentic search「压倒性地更好」，2025 年 5 月把 embedding 管线、
本地向量库、分块启发式整套移除，换成 grep。

**理由里最值得抄走的一条是成本曲线**：

```
总成本 = 建索引 + 维护 × 时间 + 每次查询 × 次数
```

前两项 grep **都是零**——活的文件系统就是索引，不需要维护，也永远不会陈旧。
向量检索要在「每次查询更省」上赢回前两项，而代码仓库的查询次数远达不到那个量级。
其余几条（代码要的是精确符号匹配而非语义邻近、分块必然切断结构、索引落后于磁盘）
都是同一件事的不同侧面：**这些问题之所以存在，是因为索引存在**。

### 也查到了索引仍然赢的三种情形

不是「RAG 没用」，是「这个规模上不划算」。索引划算的三种：

1. **超大 monorepo**（Google/Meta 那个量级），索引成本摊薄到几百万次查询上
2. **语义簇查询**——问句里没有任何具体符号名，比如「停用逻辑的边界情况在哪儿处理」，
   grep 无从下手。这条对我们成立，是唯一真正的缺口
3. **上下文额度极紧 + 模型便宜**，减少工具往返比降低延迟更重要

第 2 条留着没做。真要补，补的也该是「让模型多问几个词再 grep」，而不是建索引——
前者的成本是一次模型调用，后者的成本是那条曲线的前两项。

### 落到实现上的三个决定

- **grep 默认只回文件名**（`files_with_matches`），不回正文。这是为了逼出一次收窄：
  先看见「命中在这 5 个文件里」，再决定读哪个。默认回正文的话，
  一次宽泛搜索就能吃掉半个上下文窗口，其中九成是模型不关心的行。
- **结果按最近修改倒序**。这是不建索引之后唯一还留着的排序启发式，
  也是最划算的一个——人正在改的就是人正在问的。它同时决定了**被截断时留下的是哪一批**，
  比「按目录遍历顺序」（实质是文件名字母序）有意义得多。
- **`glob` 里不含斜杠的模式匹配文件名，而不是相对路径**。故意偏离标准 glob 语义：
  模型写 `*.java` 时想的永远是「任何地方的 java 文件」，按标准办它拿到空结果，
  而空结果和「真的没有」长得一模一样。一个技术上正确的行为，
  如果它最常见的触发方式是静默给错答案，那它就是错的。

### 换成 grep 之后，真跑一轮又抓到一个只有真跑才抓得到的 bug

单测全绿、探针也过了，于是拿真模型问了句「最近改动最多的测试文件有哪些」。
模型写了 `**/src/test/**/*.java`，**只捞回 1 个文件**——`demo/src/test/` 下那个。
顶层 `src/test/` 下的五十多个全漏了，不报错，只是少给。

原因是标准 glob 里 `**/` 是「**至少**一层目录」，而 `src` 前面没有目录可给它匹配。
同一个毛病也让 `src/**/*.ts` 匹配不到 `src/main.ts`。更糟的是，
我自己在 `GitIgnore` 里把 `**/` 实现成了「零层或多层」——
**同一个记号在同一个包里有两种意思**，`.gitignore` 挡掉的文件和 glob 认为匹配的文件对不上账。

修法是把每个 `**/` 展开成「留着」和「去掉」两种，全部试一遍。写的时候还踩了个小的：
第一版用 `String.replace` 去掉前缀，而它替换的是**所有**匹配，
`**/src/**/*.java` 会被一次砍掉两个 `**/`，生成一个谁也没要求过的模式。
改成按位置枚举组合才对。顺带发现连着的 `**/**/`  要先合并——
不合并的话组合数翻倍，撞上上限之后剩下的原样留着，等于凭空多了个「至少 N 层目录」的约束。

值得记的是**它是怎么被发现的**：59 个文件里返回 1 个，这种错误单测抓不到，
因为写测试的人和写实现的人是同一个，脑子里的 `**/` 语义也是同一个。
抓到它的是一句普通的自然语言提问，模型自己写出了那个我没想到要测的模式。

### 一条通则

**照着架构图实现之前，先查一遍这张图有没有人拆过。**
这次省掉的不是几天工期，是一条会一直缓慢漏水的管线——
索引陈旧不会报错，只会让 agent 时不时基于三天前的代码给建议。

## 2026-09-20 · 「后端收了命令，一个帧都不回」的两个假象

给圆桌接协议那天，写了个探针：起 `--serve`、连上去、发一条 `team`、把收到的帧打出来。
结果只打出一行 `features 里有 team: true`，然后**十分钟一个字都没有**。

**第一个假象：是我自己把后端卡住的。** 探针用 `Bun.spawn` 起的 java，
`stdout: "pipe"`、`stderr: "pipe"`，读到 `listening` 那行之后就再也没读过。
管道缓冲区（64KB）一满，JVM 就阻塞在一次 `write` 上——**从外面看，后端就是收了命令不回话**。
补一句「把 stdout 一直抽干」之后，现象没变，但至少这条排除了。

**第二个假象：`mvn compile` 通过，不等于我改的那个类被编译了。**
真相要打开 debug 日志才看得见：

```
Caused by: java.lang.Error: Unresolved compilation problem:
	ArrayList cannot be resolved to a type
	at dev.wiles.myagent.server.AgentServer.handleTeam(AgentServer.java:575)
```

`handleTeam` 里用了 `new ArrayList<>()` 而 `AgentServer` 没有那个 import。
javac 本该当场报错，而我跑了好几次 `mvn -o -q compile` 全是绿的——
**增量编译认为这个类没必要重编**，jar 里打进去的是一份更早的、带着「未解决的编译错误」的
class（那句错误是 Eclipse 编译器的口吻，来自 IDE 那次编译）。
错误被<b>烧进了 class 文件</b>，只在真正调到那个方法时才抛。

同一天早些时候还撞过一次同型的：测试里凭空冒出
`The import dev.wiles.myagent.llm.LlmException cannot be resolved`，
而那个类好端端在那儿——`mvn clean` 之后就没了。

### 三条

1. **子进程的 stdout/stderr 要么不接，要么一直抽干。** 接了不读，等于给它设了个定时死锁，
   而症状会伪装成「对方不响应」。
2. **排查「没反应」时，先让对方把话说出来。** 这次真正解决问题的一步是
   `-Dorg.slf4j.simpleLogger.defaultLogLevel=debug` 加上把 stderr 落到文件——
   在那之前的所有推断都建立在「我猜它卡在哪儿」上。
3. **`mvn compile` 绿 ≠ 你改的那个类被编译了。** 改完动不了的时候，
   在怀疑自己的逻辑之前先 `mvn clean`。判据很好认：**报错指向的那行代码和你看到的对不上**，
   或者错误信息的口吻不是 javac 的。

## 2026-09-20 · 提示词变量的值里带占位符，既不会被替换，也不会报错

做角色化的时候，本来想把验证角色那两行结论（`结论: 通过` / `结论: 不通过`）
从 `TaskPrompt` 的常量插值进 `roles/verifier.md`，写成 `{{@verdictPass}}`。
差一点就这么写了。

**`PromptAssembler` 有两道不变量，这条路恰好从两道中间穿过去。**
它查「关键段缺没缺」，也查「有没有没填的占位符」——后者正是为这种事准备的。
但它的替换是**对模板扫一遍**：`Matcher.appendReplacement` 把变量值写进输出缓冲，
matcher 自己继续在原模板上走。于是**填进去的那段文字根本不在扫描范围内**——
里面的 `{{@verdictPass}}` 不会被替换，也不算「没填的占位符」，
一路原样送到模型面前。

实测过了：

```
装配没抛异常
结果里还留着字面占位符: true
```

角色正文是当变量填进 `modes/task.md` 的，所以它属于「被填进去的那段」。
结论是**角色的 md 里不许出现 `{{@}}`**，那两行结论写成字面量，
两处对不上的风险改由单测钉住（`AgentRolesTest.verifierPromptDeclaresTheVerdictLines`）。

留给下次的一条：**校验发生在哪一层，决定了它管得着什么**。
装配器查的是「模板」，不是「最终文本」；一份查过的提示词里仍然可能有字面占位符。
要真的兜住，得在拼完之后再扫一遍成品——不过那样又会把记忆正文里用户自己写的
`{{...}}` 卡住（那个坑代码注释里已经记着了）。所以这里选的是约定加测试，不是加一道检查。

## 2026-09-20 · 退出 myagent 会盖掉终端里原有的内容

**现象**：退出之后，跑 myagent 之前敲的那几条命令不见了，看起来像触发了 `clear`。

**不是清屏。** 用户在自己的 Terminal.app 里用 `script` 抓了 315KB 字节流，
全程 **0 个 `ESC[2J`、0 个 `ESC[3J`** —— 谁都没清屏。而 `vim` 在同一个终端里退出得好好的，
说明终端的备用屏还原是正常的。

**是覆盖写。** 真正的线索是收尾信息落在**第 1 行**。要是主屏被正常还原，
它该接在 `myagent-tui` 那条命令后面。抓包里进备用屏之前这一段：

```
ESC[H          ← 光标挪到左上角做宽度探测
ESC]66;w=1; ESC\
ESC[6n
ESC[H          ← 又挪到左上角
ESC]66;s=2; ESC\
ESC[6n
ESC[u          ← 用 CSI u（SCORC）把光标还回去
ESC[?1049h     ← 进备用屏：终端在这一刻把光标位置存下来
```

`CSI s` / `CSI u` 是 ANSI.SYS 风格的存取光标，**macOS Terminal.app 不认**（它只认 `ESC 7` / `ESC 8`）。
于是 `ESC[u` 是个空操作，光标停在 (1,1)，被 `?1049h` 存了下来，退出时 `?1049l` 忠实地还回来。
接着收尾两行盖掉第 1、2 行，shell 提示符盖掉第 3 行——那三行正好是用户的 `cd` 记录。

**为什么查了这么久**：tmux 和 iTerm2 都实现了 `CSI s`/`CSI u`，在那儿**怎么都复现不出来**。
我在 tmux 里用真的启动脚本、真的对话、还中途改了三次窗口大小，内容全须全尾。
最后是靠用户终端里的抓包定位的。

### 三条留给下次的

1. **"屏幕没了"先分清是"清掉了"还是"被盖了"**。两者的字节特征完全不同
   （`2J`/`3J` vs 光标位置），修法也完全不同。看收尾输出**落在第几行**是最快的判据。
2. **终端兼容问题，在自己的终端里复现不出来是常态**。`script` 抓用户那侧的字节流，
   是唯一能绕过"我这儿是好的"的办法。pty 抓包看不到屏幕状态，但看得到字节——够用了。
3. **别用 `ESC 7`/`ESC 8` 去对抗备用屏**。`?1049h`/`?1049l` 用的就是同一个保存槽位，
   存进去会被覆盖。要自己记位置就问绝对坐标（`ESC[6n` → `ESC[行;列R`），
   存成两个数字放在自己的变量里，谁也动不了。

### 顺带踩的一个坑

问完光标顺手 `stdin.pause()`，结果在**终端不回话**那条路上等于把键盘关了——
界面照常画出来，但一个键都不响应，连 Ctrl-C 都退不掉。
借了状态就得原样还回去，"还回去"不等于"设成某个看起来合理的值"。

## 2026-09-20 · 1M 窗口下，按块数报压缩进度等于没有进度

**背景**：给 `/compact` 加进度条。

map 的块预算是 `maxTokens × 0.25`，1M 窗口下就是 250k token——
**整段会话通常只切出一块**。纯按块数报进度的话，条会在 0% 上干等几十秒然后直接跳 100%。

所以进度分两层：外层是块 `i/N` + reduce 那一步（结构性的，准确），
内层跟着流式输出走（已经吐了多少字 ÷ 按输入规模估的预期长度）。
内层的分母是估的，所以界面上那一行写着「进度为估算」——
**让人以为这是精确进度，比没有进度条更糟**。

实打一次（5 轮对话后 `/compact`）：1 块，33 个不同档位，0%→99% 用了 2.1 秒，99% 正好撞上收尾。

### 换流式带来的代价，差点漏掉

改用流式接口取进度时，把 `DeepSeekClient` 的**重试**一起弄丢了——
流式那条路刻意不重试（内容可能已经打到屏幕上，重来会把前半段重复输出一遍）。
而摘要特别输不起这个：调用失败会降级成一段占位文本，**而段是一辈子缓存的**，
一次转瞬即逝的 429 就能让这段历史永久变成「（摘要没能生成）」。

结论是按"有没有人在看进度"分流：没人看（后台预压缩，绝大多数情况）走原来带重试的非流式；
有人看时流式，失败了再退回非流式试一次。

**换传输方式的时候，要把那条路上附带的保障一并清点一遍。**

## 2026-09-20 · 两个界面在同一个键位上行为不一致

终端版（`Repl` + `LineReader`）的 Ctrl-C 一直是对的：跑着就中断、有字就清行、空行连按两次才退。
而 TUI 的入口接到 Ctrl-C 直接 `shutdown()`——因为那个 handler 站在 Solid 组件树外面，
**看不见「正跑着一轮」也看不见「输入框里有字」**。看不见的东西自然也保护不了。

一次跑了两分钟的任务，手一抖整个会话就没了。

同一个项目里两个界面在最基本的键位上行为不一致，比任何一种行为本身都更糟——
换个界面就得重新学一遍手感。新界面的默认行为要照着老界面抄，不是重新发明。

## 2026-09-19 · 写入路径完整、读取路径缺席

这一轮撞见三次同一类 bug，值得单独记一条。三个成熟度：

1. **从没接上**——写了存档，没有任何地方调 `load`
2. **接到了错的对象上**——存的和读的不是同一份数据
3. **接上了但字段不全**——`SessionSnapshot` 存了 `segments`，却没存 `summary` 和 `coversUpTo`

第 3 种最难查：**单测全绿，因为它测的是往返，而往返的两头用的是同一组字段**。
只有真跑一次 `/resume` 才暴露——恢复之后 `hasCompacted()` 报 false、钉住块不生成、
尾巴从 0 起，下一轮白跑一次 reduce。

**存档类的改动，测试要跨"进程重启"这条线，而不只是跨"序列化再反序列化"。**

## 2026-09-19 · 工作区全绿 ≠ 每个 commit 都好

拆 commit 的时候，工作树是最终状态、测试全绿，但**第 3 个 commit 单独拿出来是红的**——
tsc 过不了，因为一个 hunk 被 `git apply --cached --recount` 放错了位置。

从那以后拆 commit 的做法改成：**从 HEAD 分层重建**，每层写完跑一次全量测试再提交，
最后再用 `git worktree` 把每个 commit 单独 checkout 出来各验一遍。
代价是多跑几轮测试，换来的是"每个 commit 都能独立编译和通过"这句话是真的。

另：`git stash --keep-index` 会把工作树搅坏（`pop` 之后留下冲突标记，而 `git status` 里看不出 `UU`），
拆 commit 别用它。
