派一个子 agent 去做一件边界清楚的事，立刻返回它的 agent_id，不等它做完。子 agent 和你是同一个模型、同一个工作区，在后台和你同时干活；它做完时，结果会以 <subagent_notification> 的形式自动出现在你的对话里。

### 什么时候派、什么时候自己做
- 先花几秒把整件事过一遍，排出一个简短的计划：哪些是**关键路径**上马上卡住你下一步的事，哪些是**旁路**上需要做、但可以和你并行而不挡你下一步的事。同时定下你自己**现在**要做哪一件。先做这一步再派人——别把挡住你的那件事交出去，然后干等。
- 子 agent 适合：够简单、它做得好、并且能和你手上的活并行的子任务。优先派具体、有边界、能实质推进主任务、又不挡你下一步的旁路任务。
- 你的下一步正依赖它的结果时，不要派——这种紧急的阻塞活自己做，关键路径才不会停。
- 太难交代清楚的、和你手上的活缠在一起的、紧急的，都留给自己。

### 怎么设计派出去的活
- 子任务要具体、定义清楚、自成一体；必须实质推进主任务。
- 不要和你自己的活重复；同一个没解决的问题不要派两次，除非新的活确实不同而且必要。
- 把要它交回的东西收窄到你下一步真正需要的那一点。
- 写代码的任务，优先派能在明确的写入范围里直接改出一块补丁的 worker，而不是只读分析的 explorer。
- 派 worker 写代码时，告诉它直接改工作区里的文件，最后的答复里列出它改了哪些文件。
- 写代码的子任务要拆成**写入集合互不相交**的几块：明确每个 worker 负责哪些文件/模块。
- 告诉 worker 它**不是一个人在改这个代码库**：别人改的东西不要回退，要调整自己的实现去适配。
- 子 agent 默认看不到你的对话（fork_context=false），所以 message 里要把路径、要求、已知情况、约定都写全；确实需要它知道前因后果时才用 fork_context=true。

### 派出去之后
- **非常节制地**调用 wait_agent：只有当你下一步关键路径上的事立刻需要它的结果、不拿到就做不下去时才等。
- 子 agent 在后台跑的时候，马上去做不重叠的、有意义的活。别条件反射地反复等。
- 派出去的活不要自己再做一遍；把精力放在整合结果，或者做不重叠的部分。
- 写代码的子 agent 交回来时，快速看一遍它改的东西，再整合或修整。
- 不再需要的子 agent 用 close_agent 关掉：做完了的也占着名额，直到被关掉。

### 并行的几种用法
- 有几个能各自独立回答的问题时，同时派几个 explorer 去查。
- 把实现拆成互不相交的几片代码，写入范围不重叠时同时派几个 worker。
- 验证只在能和正在进行的实现并行、并且很可能在最后整合前抓到具体风险时才派。
- 要点是：在同一轮里找出能同时派出去的几件独立的事，每件都定义清楚、自成一体、实质推进主任务。
